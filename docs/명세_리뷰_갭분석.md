## 1. 스크립트 자산 실사

### 1.1 구성

실행 스크립트 72개(`sh` 55, `ps1` 8, `bat` 4, `sql` 3, `cmd` 2). 이 중 KISA 항목코드를 보유한 것이 50개, CSV를 산출하는 것이 43개다.

항목코드 체계는 이미 확립되어 있다.

```
U-01 ~ U-67    Unix/Linux 서버
W-01 ~ W-64    Windows 서버
D-01 ~ D-26    DBMS (Oracle, MySQL, MariaDB, PostgreSQL, MSSQL, MongoDB, Redis, Tibero)
NW-xx          네트워크 장비
CA-01 ~ CA-19  클라우드 (AWS, Azure, GCP, Huawei)
PC-xx          PC (Windows, macOS)
FG-xx          보안장비
```

이는 명세 §9의 `LINUX-PASSWD-001` 형식과 다르다. **새 ID 체계를 만들 이유가 없다.** KISA 코드를 1차 키로 채택하고 플랫폼 구분이 필요한 경우에만 접미(예: `U-01@aix`)를 붙이는 편이 마이그레이션 비용과 현장 커뮤니케이션 비용 모두에서 유리하다.

### 1.2 스크립트 계열 — 3종으로 분화되어 있음

**F1 — 자체 판정형 (46개, 자산의 다수).** 팀 자체 제작 계열(SUNEEDS 배너). `result()` / `Result()` 공통 함수를 통해 화면·리포트·CSV에 동시 기록하며, **판정까지 수행한다.**

```sh
result() {
  local code="$1" sev="$2" title="$3" res="$4" comment="$5"
  case "$res" in
    GOOD)   tag="양호"     ;;
    VULN)   tag="취약"     ;;
    *)      tag="수동확인"  ;;
  esac
  ...
  echo "$code,\"$title\",$sev,$tag,\"$c\"" >> "$CSV"
}
```

내부 상태값(`GOOD`/`VULN`/`MANUAL`)과 표시값(`양호`/`취약`/`수동확인`)이 이미 분리되어 있다. 명세 §3.2가 요구하는 구조를 사실상 이미 갖췄다.

**F2 — 수집 전용 / 제3자 저작물 (7개).** 전자금융 A3S 계열(`*_finance_v3.3/v3.4`). 판정하지 않고 설정 원문을 섹션 단위로 덤프한다.

```sh
echo "[PRODUCT : $product]"
echo "[HOME    : $home]"
echo "[PATH    : $path]"
echo "[PERM    : $perm]"
```

스크립트 서두에 저작권 고지가 있다.

> 본 프로그램의 모든 저작권은 [주]에이쓰리시큐리티에 있습니다. 무단 사용·복사·도용을 허용하지 않습니다.

**이 계열은 수정·재배포 대상이 아니다.** InfraGuard는 산출물을 읽어 정규화만 하고, 스크립트 자체는 Rule Pack에 포함하지 않는 것이 안전하다.

**F3 — 조치형 (2개).** `kisa_2026_pc_windows_fix.ps1`, `kisa_2026_pc_macos_fix.sh`. 레지스트리·시스템 설정을 **변경한다.** 개발목표 §35 "진단 대상 서버의 설정을 자동 수정 금지"와 정면 충돌하므로 Rule Pack 로딩 대상에서 물리적으로 분리해야 한다.

**F4 — 기타 수집형 (19개).** `Windows_Script_2026_06.bat`(313KB, CP949, `chcp 949`, `[RESULT]_%COMPUTERNAME%_NT.txt` 파일 출력), 미들웨어(Apache/Tomcat/Nginx/IIS), 클라우드, K8s 등.

### 1.3 명세의 근본 가정 3개가 현 자산과 불일치

**불일치 ①: "Rule 하나 = 스크립트 하나"**

명세 §8의 디렉터리 구조는 `LINUX-PASSWD-001/check.sh`처럼 Rule마다 스크립트 파일 하나를 상정한다. 그러나 현 자산은 **스크립트 1개가 67개 항목 전부를 순차 점검**한다(`unix_infra_script.sh` → U-01 ~ U-67).

이를 명세대로 쪼개려면 67개 스크립트로 분해해야 하는데, 실제로는 불가능하다. 항목 간 수집 결과를 공유하기 때문이다(`/etc/passwd` 파싱 결과를 U-02·U-04·U-44·U-52가 함께 사용). 분해하면 동일 명령이 수십 회 중복 실행되어 운영 서버 부하와 실행 시간이 급증한다.

→ **`Bundle`(다항목 스크립트) 개념을 1급 시민으로 도입해야 한다.** 상세는 설계 문서 참조.

**불일치 ②: "결과는 stdout으로 온다"**

명세 §12·개발목표 §15는 stdout JSON을 전제한다. 그러나 현 자산 전부가 **파일 시스템에 산출물을 만든다.**

| 계열 | 산출물 |
|---|---|
| F1 (sh) | `./result_<HOST>_<TS>/` 디렉터리 — `report_*.txt`, `result_*.csv`, `account_detail_*.csv`, `evidence_detail_*.txt`, 최종 `*.tar.gz` |
| F1 (ps1) | `Export-Csv -Encoding UTF8` |
| F2 (A3S) | `result_<HOST>_<DATE>.txt` + `config/` 디렉터리 트리 |
| F4 (bat) | `[RESULT]_%COMPUTERNAME%_NT.txt` 등 다수 |

stdout은 사람이 보는 진행 로그(ANSI 색상 포함)일 뿐 파싱 대상이 아니다.

→ Executor의 결과 수집은 **stdout 파싱이 아니라 산출물(artifact) 수집**을 1차 경로로 설계해야 한다.

**불일치 ③: "엔진이 대상 서버에서 실행된다"**

MVP를 "현장 서버에서 실행되는 Standalone CLI"로 규정했으나, 실제 진단 대상에는 **AIX·HP-UX·Solaris**가 포함되어 있다(`aix_finance_v3.4.sh`, `hpux_finance_v3.4.sh`, `solaris_finance_v3.4.sh`, `aix_infra_scripts_2026.sh`, shebang `#!/bin/ksh`). 이들 플랫폼에 Python 런타임이나 PyInstaller 바이너리를 반입·실행하는 것은 현실적으로 어렵다.

또한 금융·공공 현장은 실행 파일 반입 심사가 스크립트 반입보다 까다롭다.

→ **엔진이 대상 서버에서 실행되지 않는 모드(Ingest)를 MVP에 포함해야 한다.** 기존과 동일하게 스크립트만 전달하고, 회수한 산출물을 진단자 PC에서 정규화·판정·리포트한다. 이것이 오히려 즉시 효용이 크다 — 현재 수작업의 대부분은 실행이 아니라 **결과 취합**이기 때문이다.

### 1.4 CSV 포맷 불일치 (4종 이상)

CSV를 산출하는 43개 스크립트의 헤더가 통일되어 있지 않다.

```
항목코드,점검항목,중요도,결과,코멘트                                        (19개)
"항목코드" "진단항목" "중요도" "진단결과" "진단내용"
"항목코드" "진단항목" "중요도" "진단결과(양호/취약)" "진단 내용"
"항목코드" "진단항목" "분야" "중요도" "점검방식" "진단결과" "판단기준" "진단내용"
항목코드,중요도,분류,점검항목,상태,점검근거,조치권고                          (PowerShell)
```

판정 어휘도 혼재한다. `양호`(69) / `취약`(68) / `수동확인`(49) / `수동`(59) / `N/A`(30) / `해당없음`(13) / `N-A`(1). 영문 상태값도 `GOOD`(52) / `VULN`(45) / `MANUAL`(46) / `NA`(63)로 산재한다.

→ 파서를 하드코딩하지 말고 **헤더 기반 자동 판별 + 프로파일 매핑(YAML)** 구조로 만들어야 한다. 새 스크립트가 추가돼도 프로파일만 추가하면 되도록.

### 1.5 인코딩·셸 실사

| 항목 | 실측 |
|---|---|
| shebang | `bash` 35, `sh` 12, `ksh` 2, `zsh` 2(macOS), `/usr/bin/sh` 1 |
| 인코딩 | UTF-8 다수, **UTF-8 BOM** 2(ps1), **CP949/ISO-8859** 2(bat), CRLF 혼재 |
| bat | 내부에서 `chcp 949` 실행 — 출력은 CP949 확정 |
| sh 계열 | 대부분 `export LANG=C` 선언 — 명세 §17과 이미 부합 |

명세 §16의 인코딩 매트릭스는 실제 자산과 정확히 일치한다. 이 부분은 명세가 옳다.

### 1.6 자산 위생 문제

- **버전 스프롤**: `mysql_infra_script` v2·v3·v4·v5 + 무버전, `tomcat` / `tomcat_old`, `apache_security.sh` + `.bak`, `iis` / `iis/iis`
- **md5 완전 중복 4쌍** (동일 파일이 두 경로에 존재)
- **압축 파일 중첩**: `kubernetes.zip`, `tomcat.zip`, `apache_old.zip`, `PC진단 스크립트.zip` 등이 디렉터리와 함께 존재

→ Rule Pack 구성 시 **어느 파일이 정본인지 결정하는 작업이 선행되어야 한다.** 이 결정은 자동화할 수 없고 사람이 해야 한다. 정본 확정 전에 Rule Pack을 만들면 잘못된 버전이 고정된다.

## 3. 갭 항목

우선순위: **P0 = MVP 착수 전 확정 필수**, P1 = Phase 2 전, P2 = 이후.

### 3.1 자산 실사에서 새로 도출된 항목

**G-25 (P0). 다항목 번들 모델 부재.**
§1.3 불일치 ①. 명세의 Rule 모델로는 현 자산을 담을 수 없다. `Bundle` = 1회 실행으로 N개 Rule 결과를 산출하는 단위. Rule은 판정 메타데이터(이름·심각도·조치권고·근거)만 보유하고, 결과 채움은 Bundle이 담당하는 구조가 필요하다. Bundle이 선언한 `provides` 목록 중 산출물에 나타나지 않은 Rule은 자동으로 UNKNOWN 또는 ERROR로 처리한다(누락 은폐 방지).

**G-26 (P0). 산출물(artifact) 수집 계약 부재.**
§1.3 불일치 ②. `collect.artifacts`에 glob 패턴·파서·인코딩을 선언하고, Executor가 격리된 작업 디렉터리에서 수집하는 규약이 필요하다. tar.gz 자동 해제도 포함.

**G-27 (P0). Ingest 모드 부재.**
§1.3 불일치 ③. 엔진이 대상 서버에서 실행되지 않고, 회수한 산출물만 처리하는 경로. AIX·HP-UX·Solaris 대응과 반입 제약 회피의 유일한 현실적 해법이며, 동시에 **가장 빨리 효용이 나오는 기능**이다.

**G-28 (P0). CWD 오염.**
현 스크립트는 실행 위치에 `result_*` 디렉터리와 `config/` 트리를 만들고, 일부는 기존 결과 파일을 `rm -rf` / `del` 한다. 개발목표 §13 "현재 디렉터리 영향 방지"를 지키려면 Executor가 Bundle마다 격리 작업 디렉터리를 만들어 그 안에서 실행해야 한다. 실행 위치를 그대로 두면 **다른 Bundle의 산출물을 삭제할 수 있다.**

**G-29 (P0). 스크립트 인자 전달 수단 부재.**
클라우드 스크립트는 `-a <profile> -r <region>` 인자를 받는다(`cloud_aws_full_infra_script.sh`). DB 스크립트는 `ORACLE_HOME`·`ORACLE_SID`·`DBCONN` 환경변수를 요구한다. Rule/Bundle 스키마에 `params`(정의) + 실행 시 `--param k=v` 주입 경로가 필요하다. 이때 값이 셸 명령 문자열로 연결되지 않도록 **인자 배열로 전달**해야 한다(개발목표 §27 Command Injection).

**G-30 (P0). 조치형 스크립트 격리 수단 부재.**
`*_fix.ps1` / `*_fix.sh`가 자산에 섞여 있다. Rule Pack 로더가 `side_effects` 미선언 또는 `write` 선언 스크립트를 기본 거부하고, `--allow-remediation` 같은 별도 경로에서만 취급하도록 강제해야 한다.

**G-31 (P1). 제3자 저작물 취급 정책 부재.**
A3S 계열은 저작권이 외부에 있다. Rule Pack에 스크립트 본문을 포함하지 말고, 산출물 파서(Ingest 어댑터)만 제공하는 방식으로 분리한다. Rule Pack manifest에 `license` / `redistributable` 필드를 둔다.

**G-32 (P1). 정본 스크립트 미확정.**
§1.6. 버전 스프롤·중복이 정리되지 않은 상태에서 Rule Pack을 구성하면 잘못된 버전이 고정된다. Rule Pack 착수 전 정본 선정이 선행 작업이다.

### 3.2 v1에서 이어지는 항목

**G-01 (P0). Status 판정 우선순위 미정의.** 권고 순서:

```
1. Prerequisite 미충족                   → SKIPPED
2. Timeout / crash / 실행 불가            → ERROR
3. exit code 정책 위반                    → ERROR
4. 산출물 부재 / 파싱 실패                 → ERROR
5. Bundle이 provides 했으나 결과 누락      → UNKNOWN (누락 사유 기록)
6. 파싱 성공, 판정 필드 부재/형식 불일치     → UNKNOWN
7. Rule이 manual 선언                     → UNKNOWN
8. condition 평가                         → PASS / FAIL
```

stderr 출력만으로는 Status를 바꾸지 않고 보존한다.

**G-02 (P0). exit code 해석 정책 부재.** 현 자산 실측 결과 F1 계열은 항목별 판정을 CSV에 쓰고 종료 코드는 스크립트 전체 성패만 나타낸다. 즉 **exit code는 판정 신호가 아니다.** 다만 클라우드 스크립트는 인자 오류 시 `exit 1`을 낸다. Bundle metadata에 다음을 둔다.

```yaml
exit_code:
  policy: strict          # strict | ignore | map
  success: [0]
  map: {2: SKIPPED}
```

**G-03 (P0, 최우선). 출력 파서 유형 미정의.** `json` 단독으로는 현 자산 43개 CSV를 하나도 못 읽는다. 최소 5종 필요.

| 파서 | 용도 |
|---|---|
| `legacy_csv` | F1 계열 CSV. 헤더 자동 판별 + 프로파일 매핑 |
| `section` | F2/A3S `[PRODUCT: …]` 블록 덤프 |
| `json` | Native Rule 표준 |
| `keyvalue` | 신규 sh Rule의 최소 비용 경로 |
| `raw` | 파싱 없이 evidence 보존 → UNKNOWN |

**G-04 (P0). Evaluator 표현식 언어 미정의.** `eval` 금지. AST 화이트리스트 평가기 필요. 다만 §1.2에서 확인했듯 F1 계열은 이미 스크립트가 판정하므로, MVP에서 표현식 평가가 필요한 Rule은 소수다. 우선순위를 P0으로 두되 구현 범위는 최소로 잡는다.

**G-05 (P0). 판정 어휘 매핑 표준 부재.** 실측 어휘가 7종 이상 산재(§1.4). 매핑 테이블을 파서 프로파일에 두고 미등록 어휘는 UNKNOWN + 경고로 처리한다.

```
양호 / GOOD           → PASS
취약 / VULN           → FAIL
수동 / 수동확인 / MANUAL → UNKNOWN
N/A / N-A / NA / 해당없음 → SKIPPED
(미등록 어휘)          → UNKNOWN + parse_warning
```

**G-06 (P0). Result Schema에 evidence 필드 부재.** F1 계열의 `코멘트` 컬럼이 곧 판단 근거이며 보고서 필수 요소다. `evidence` 필드 및 `evidence_ref`(대용량 증적 파일 참조)를 추가한다.

**G-07 (P1). 출력 크기 상한 미정의.** `evidence_detail_*.txt`는 수 MB에 달할 수 있다. 인라인 상한(예: 64KB/Rule)을 두고 초과분은 파일 참조로 전환한다.

**G-08 (P0). 민감정보 마스킹이 키 이름 기반에 그침.** F1 스크립트는 `/etc/shadow`·`/etc/passwd`·SNMP community·계정 목록을 evidence에 포함한다. 값 패턴 기반 마스킹(`$6$…` 해시, `-----BEGIN … PRIVATE KEY-----`, `AKIA…`, JDBC URL 내 password, SNMP community)을 Result Engine normalize 단계에서 강제한다. **결과 파일이 고객사 외부로 반출되므로 사고 직결 항목이다.**

**G-09 (P0). 프로세스 트리 종료 미정의.** F1 스크립트는 `find /` 전체 순회를 포함해 장시간 실행되는 자식을 다수 생성한다. Timeout 시 프로세스 그룹(Linux) / Job Object(Windows) 단위 종료 필수.

**G-10 (P1). PowerShell 실행 옵션 미명세.** `-NoProfile -NonInteractive -NoLogo -ExecutionPolicy Bypass -File`(프로세스 단위). Constrained Language Mode 점검 추가.

**G-11 (P0). 실행 인코딩 세부 규칙 미정의.** bat은 `chcp 949` 후 출력 → CP949 고정. ps1은 BOM. 산출물 파일별 인코딩은 파서 프로파일에서 후보 목록(`[utf-8-sig, utf-8, cp949]`)으로 선언하고 순차 시도한다.

**G-12 (P1). 자동 권한 상승 정책 미정의.** 자동 승격 금지. `--sudo` 명시 시에만. 실행 전 확인 가능한 권한 부족 → SKIPPED, 실행 중 EACCES → ERROR.

**G-13 (P1). `/tmp noexec` 미고려.** doctor 점검 항목 추가 + `--workdir` 옵션.

**G-14 (P1). 동시 실행 정책 미정의.** MVP 순차 고정.

**G-15 (P1). 전체 Scan Timeout 부재.** Bundle 단위 실행이므로 Bundle timeout(예: 1800초)과 Scan 전역 상한을 둔다.

**G-16 (P0, 격상). Unix 계열(AIX·HP-UX·Solaris) 부재.** §1.3 불일치 ③. Environment Detector OS 열거형과 Rule `platform`에 포함. 실행 엔진은 Ingest 모드로 대응.

**G-17 (P1). Compatibility WARN 의미 미정의.** 실행하되 `compat_warnings[]` 첨부.

**G-18 (P1). CLI exit code 규약·기계 판독 출력 부재.** `--json`, `--no-color`, `--quiet` + exit code 규약.

**G-19 (P0). Read-only 보장 수단 부재.** G-30과 통합. `side_effects` 선언 필수화 + 위험 패턴 정적 탐지.

**G-20 (P1). DB Credential 입력 경로 미정의.** 현 자산은 `DBCONN='/ as sysdba'`(OS 인증) 기본. 이 방식을 표준으로 채택하고, 필요 시 stdin 전달만 허용한다. `user/pass@tns` 인자 형식은 `ps` 노출로 금지.

**G-21 (P1). DB 접속 방식 결정 필요.** MVP는 CLI 의존(현 자산이 `sqlplus` 기반), Native Rule에서 드라이버 도입.

**G-22 (P1). Rule Pack 무결성 검증 수준 미확정.** manifest에 SHA-256, 서명은 P2.

**G-23 (P1). Profile 문법 미정의.** 제외 문법·상속 정의.

**G-24 (P1). Rule Schema 검증 도구 부재.** `infraguard rules --validate` + JSON Schema.

## 4. 현장 리스크

**R-01. PyInstaller glibc 호환.** 최신 배포판 빌드 바이너리는 RHEL 7 이하에서 실행 불가. `manylinux2014`급 컨테이너로 빌드 환경 고정. 자산에 CentOS 6/7 대상 스크립트가 존재하므로 실재하는 위험이다.

**R-02. AIX·Solaris에서의 Python.** PyInstaller 비공식 지원. → Ingest 모드(G-27)로 회피.

**R-03. Windows EDR/AV 오탐.** onefile 차단 흔함. onedir + 코드 서명 검토.

**R-04. evidence 유출.** G-08 참조. 최우선 보안 항목.

**R-05. 진단 계정 세션 제한.** `TMOUT`·`ulimit -t`가 Scan 중 프로세스를 종료시킨다. F1 스크립트는 수십 분 실행되므로 실재 위험. 부분 결과 체크포인트 저장 필요.

**R-06. 시각 기준 미명세.** ISO 8601 + 오프셋 고정.

**R-07. 스크립트 실행 시간.** `find / -perm -2 -type f` 등 전체 파일시스템 순회가 다수 포함되어 있다. 대용량 스토리지 서버에서 수십 분~수 시간 소요될 수 있으며, 이는 Timeout 기본값 설계에 직접 영향을 준다. Bundle 기본 timeout을 300초로 두면 대부분 실패한다. **1800초 이상을 기본값으로 잡아야 한다.**
